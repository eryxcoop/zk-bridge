# Documentation for ZK Bridge - Milestone 5

This is the main document for the milestone 5 delivery of our ZK bridge. In this milestone we present the
circuits that will be used to generate the ZK proofs required by the bridge.

All these proof verifications are currently mocked in our bridge validators (the validators verify toy proofs
as a placeholder for the real proof). In this milestone we only present the circuits to generate the real proofs
but we do not modify the validators to verify the proofs generated by these new circuits. That is non-trivial work
as it requires dealing with the size and execution unit limitations of Cardano transactions, and is part of the
final milestone of our project.

# ZK Proofs needed for the bridge

As discussed in previous milestones, we need 3 ZK proofs to safely mint funds from a chain
isomorphic to Cardano.

- Proof that the multi-signature of a Mithril certificate is valid.
- Proof that a transaction is present in the Mithril transaction snapshot.
- Proof that the used transactions set was updated correctly.

## Validation of Mithril Certificate multisignature

This proof corresponds to the Mithril standard-certificate validation path used by the bridge, centered on
`verify_mithril_standard_certificate`.

At the scope of milestone 5, this document focuses on the proof-generation side only: the real prover circuit is
identified and described here, but its end-to-end on-chain verification wiring is intentionally left for a later
milestone.

To get a real proof we took advantage of a change Mithril made to their multi-signature validation
scheme, replacing their concatenation proof mechanism with a SNARK generated by Halo2. This change is
not yet in production in Mithril, but it is progressing steadily and updates are published regularly;
the ongoing work can also be followed in [their repository](https://github.com/input-output-hk/mithril)
on a daily basis.

The circuit used can be found in the Mithril repository at `mithril-stm/src/circuits/halo2/circuit.rs`.
It takes as input a witness derived from the certificate signatures and message. To generate the proof,
the circuit iterates over the certificate signatures and verifies for each one:

- That the signature is valid.
- That the signer's Merkle path is valid in the Mithril stake distribution Merkle tree.
- That the signer won the lottery (i.e. is eligible to sign the certificate).

## Transaction inclusion in Mithril snapshot

The proof generated by this circuit is also used in the bridge minting validator, specifically in the
`verify_transaction_is_present_in_snapshot` function.

In this case we wrote a circom circuit which can be found in the `circuit_transaction_snapshot` folder. 
This circuit takes a Mithril transaction snapshot certificate — whose message is a Merkle root of the Cardano 
transaction snapshot for the corresponding epoch — together with a Merkle path also provided by Mithril. The circuit 
proves that a transaction with a given ID is present in that snapshot by verifying the supplied Merkle path against the
root.

### Blake2s circuit

Mithril uses `Blake2s` as the hash function for its Merkle trees. This function has no standard
implementation in `circomlib`, so we had to use an alternative. We chose the implementation from
[this repository](https://github.com/bkomuves/hash-circuits), which we tested thoroughly.

## Transaction set update

This proof is used in both the unlocking and minting scripts (in the
`locking_tx_hash_is_added_to_the_used_txs_set` function) and its purpose is to prevent double spending:
preventing a burn transaction made on the other chain from being used to unlock funds twice on Cardano,
and preventing a locking transaction made on Cardano from being used to mint funds twice on the other
chain.

To achieve this, we must maintain a set of already-used transactions. To prevent this set from growing
unboundedly, we represent it as a Merkle tree.

In this case, however, we do not need to prove that a transaction belongs to the set represented by the
Merkle tree; instead we need to prove that the transaction is not yet in the set, and additionally that
the set was then updated to include it.

For this we use a sparse Merkle tree, which allows us to prove both the inclusion and the exclusion of an
element in a set.

The circuit used to generate this proof can be found in the `circuit_inclusion_exclusion` folder,
specifically in the `TxSetUpdate` component.

## Testing of transaction set update and transaction inclusion in Mithril snapshot

Both circuits (`circuit_transaction_snapshot` and `circuit_inclusion_exclusion`) share the same testing
structure. Each has two scripts:

- `scripts/build_groth16_artifacts.sh`: compiles the `.circom` circuit using the `circom` compiler and
  produces the artifacts needed for proof generation in the `groth16_artifacts/` folder:
  - `.r1cs` with the circuit constraints
  - `.wasm` with the witness calculator
  - `.sym` with the symbol map

  The script automatically detects whether the `.circom` file or any of its dependencies have changed by
  comparing timestamps, and only recompiles when necessary.

- `scripts/run_e2e_test.sh`: runs the full testing pipeline in three steps:
  1. Calls `build_groth16_artifacts.sh` to ensure the artifacts are up to date.
  2. Runs the Rust binary `generate_test_witness_for_circuit`, which constructs a synthetic witness from
     hardcoded values (a fixed tx hash, known siblings, manually computed hashes) and writes it to
     `final_fixture/input.json`. This binary makes no network requests and uses no Mithril logic; its
     sole purpose is to produce a valid input to verify that the circuit works correctly.
  3. Runs the Rust binary `arkworks_circom_fixture_export` with that `input.json`. It loads the `.wasm`
     and `.r1cs`, calculates the witness by executing the WASM, generates a Groth16 proof using the
     `ark-circom` library, verifies that the proof is valid, and writes the output artifacts
     (`proof.json`, `public.json`, and the verification key in Aiken format).

If `run_e2e_test.sh` completes without error, the circuit compiles, the witness is satisfiable,
and the Groth16 proof verifies correctly.

Note that `mithril_legacy_tx_membership.rs` — which normalizes real proofs from the Mithril aggregator
into the circuit's input format — is **not involved** in this testing flow. It is only used by the
production operator (`zk-bridge-operator`) when generating a proof from a real Mithril
certificate.

## Operator experiments with real Mithril data

Alongside the local fixture flows above, milestone 5 also includes the operator experiment in
the `zk-bridge-operator` crate. This binary connects to a Mithril aggregator and exercises the
same two bridge-facing proof-generation paths using real Mithril responses.

Its two main commands are:

- `relayer sync-certificates`
- `tx prove <transaction-hash>`

For the operator contract and generated artifacts, see:

- [`zk-bridge-operator/README.md`](zk-bridge-operator/README.md)

# End-to-end test flows

The main milestone-5 flows were revalidated successfully:

- `circuit_transaction_snapshot/scripts/run_e2e_test.sh`
- `circuit_inclusion_exclusion/scripts/run_e2e_test.sh`
- `zk-bridge-operator tx prove <transaction-hash>`

To run the tests for both circuits from the repository root:

```bash
cd circuit_transaction_snapshot && ./scripts/run_e2e_test.sh
cd circuit_inclusion_exclusion  && ./scripts/run_e2e_test.sh
```

To test the operator against a real Mithril aggregator:

```bash
cd zk-bridge-operator
cargo run -- relayer sync-certificates
cargo run -- tx prove <transaction-hash>
```
