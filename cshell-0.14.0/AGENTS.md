# AGENTS.md

## Purpose

This directory is a local clone of `txpipe/cshell` pinned to the exact release
currently installed via `tx3up stable` in this workspace:

- repo: `https://github.com/txpipe/cshell`
- tag: `v0.14.0`
- commit: `5134bbc05ede93cf7c0639bbac8cddc3bc54656b`

We cloned it here to investigate and, if possible, fix a compatibility bug that
is currently blocking the bridge runtime flow in this repo.

## The problem we are trying to solve

The failing command is:

- `cshell tx invoke`

Observed runtime error:

```text
❗️ error: invalid param type
```

This is currently reproducible outside the bridge with a tiny standalone repro:

- directory:
  - `../tx3_cshell_invalid_param_type_repro`

That repro contains two minimal tx templates:

- `publish_ref_script_repro`
- `plain_transfer_repro`

Both fail with the same `invalid param type` error when invoked through
`cshell tx invoke` against the **namespaced TII** generated by current
`trix build`.

## Why this looks like a cshell/TII compatibility bug

We isolated the failure away from the bridge codebase:

- the minimal repro does **not** use:
  - custom Tx3 records
  - Groth16
  - Mithril data
  - bridge scripts
  - large integers
- it still fails with:
  - `invalid param type`

We also verified a strong signal around TII format differences:

- The new namespaced TII generated by current `trix` triggers the error in
  `cshell tx invoke`.
- In the bridge project, the older flat TII file:
  - `.tx3/tii/main.tii`
  behaved differently and got past this exact param-typing failure.

Current hypothesis:

- `cshell 0.14.0` is not correctly consuming the namespaced TII shape emitted
  by `trix 0.25.1`

This is no longer just a hypothesis. The exact root cause identified here is:

- `cshell-0.14.0` depends on:
  - `tx3-sdk 0.9.2`
- `tx3_sdk::tii::ParamType::from_json_schema(...)` only recognizes:
  - `https://tx3.land/specs/v1beta0/core#Bytes`
  - `https://tx3.land/specs/v1beta0/core#Address`
  - `https://tx3.land/specs/v1beta0/core#UtxoRef`
- current `trix build` emits namespaced refs such as:
  - `https://tx3.land/specs/v1beta0/tii#/$defs/Bytes`
  - `https://tx3.land/specs/v1beta0/tii#/$defs/Address`
  - `https://tx3.land/specs/v1beta0/tii#/$defs/UtxoRef`
- that mismatch triggers:
  - `InvalidParamType`
  - surfaced by `cshell` as:
    - `invalid param type`

## Relevant files inside cshell

The main execution path for `tx invoke` in this version is:

- `src/tx/invoke.rs`
  - CLI entrypoint for `cshell tx invoke`
- `src/tx/common.rs`
  - `prepare_invocation(...)`
    - loads the TII via:
      - `tx3_sdk::tii::Protocol::from_file(...)`
  - `load_args(...)`
    - reads `--args-json` / `--args-file`
  - `inquire_missing_args(...)`
    - fills any missing params interactively using `ParamType`
  - `resolve_tx(...)`
    - turns the invocation into a TRP resolve request
- `src/tx/resolve.rs`
  - same argument preparation path, but without signing/submitting

Important code facts directly verified here:

- `prepare_invocation(...)` in `src/tx/common.rs`
  parses the TII first:
  - `tx3_sdk::tii::Protocol::from_file(tii_file).context("parsing tii file")?`
- `load_args(...)` just parses the user JSON and calls:
  - `invocation.set_args(value);`
- `inquire_missing_args(...)` matches over:
  - `ParamType::Address`
  - `ParamType::Integer`
  - `ParamType::UtxoRef`
  - `ParamType::Boolean`
  - `ParamType::Bytes`
- the observed `invalid param type` error therefore likely originates
  inside `tx3_sdk::tii` while mapping param schemas, before provider resolution.

## Fix implemented locally in this clone

The minimal local fix implemented here is:

- in `src/tx/common.rs`
  - replace the direct `Protocol::from_file(...)` path with:
    - read TII file as JSON
    - recursively normalize only these refs:
      - `.../tii#/$defs/Bytes` -> `.../core#Bytes`
      - `.../tii#/$defs/Address` -> `.../core#Address`
      - `.../tii#/$defs/UtxoRef` -> `.../core#UtxoRef`
    - then call:
      - `tx3_sdk::tii::Protocol::from_json(...)`
- no dependency bump was used
- no `tx3-sdk` code was modified
- the workaround is intentionally surgical and local to `cshell`

- legacy `core#...` refs still work

  - passes

Validated runtime behavior with the external repro:

- using the locally built `cshell-0.14.0` binary against:
  - `../tx3_cshell_invalid_param_type_repro`
- both:
  - `publish_ref_script_repro`

That is the expected success condition for this fix:

- param typing is accepted
- any later failure is provider/runtime, not TII schema compatibility

## Bridge-specific relevance

This bug blocks the experimental bridge flow:

- `bridge-aiken/scripts/bridge.sh genesis_dual_signature`

That flow now already bypassed the older i128 limitation by moving large Jubjub
public inputs from runtime `Int` to runtime `Bytes`, but it still reaches the
same `cshell tx invoke` failure later.

So even though the original blocker showed up inside `bridge-aiken`, the
current target here is a smaller upstream-compatible fix in `cshell`.
