# Documentation for ZK Bridge - Milestone 6

In the previous milestone we implemented the ZK proofs that need to be
verified in the bridge's unlocking and minting contracts. The contracts
verify two Groth16 proofs that check that the locking/burning transaction
set has been updated and that a transaction is present in the Mithril
transactions snapshot. In addition, our contracts must verify the Halo2
proofs generated by Mithril for the stake distribution and transactions snapshot
certificates, each of which checks that the corresponding Mithril certificate
aggregation is valid.
It was also necessary to take handle the bootstrap stake distribution genesis

The goal of milestone 6 is to be able to generate transactions that take
these proofs and the corresponding Mithril certificates as input and that carry scripts
that verify them. All of this while staying within Cardano's
execution-unit and maximum-transaction-size limits.

# Integration of zk proofs in the transactions flow

Integrating these new proofs forced us to adapt our validators and the
overall bridge transaction flow so that everything keeps working.

The principal challenge we faced was the fact that the
aggregation proof produced by Mithril is generated with Halo2. That
meant we needed to verify a Halo2 proof in Cardano. That's something we
hadn't done in previous milestones. And forced many changes in our bridge.

## Verifying Halo2 proofs

For this, we used the
[plutus-halo2-verifier-gen](https://github.com/input-output-hk/plutus-halo2-verifier-gen/tree/main)
package built by IOG. The package needed modifications to be able to
verify proofs generated by Midnight's Halo2 fork (`midnight-proofs`),
which is the one used by Mithril, since `plutus-halo2-verifier-gen` is
designed for proofs generated by `halo2-proofs`. The full list of
changes we had to make is documented in
[plutus-halo2-verifier-gen/PLUTUS_HALO2_VERIFIER_CHANGES.md](plutus-halo2-verifier-gen/PLUTUS_HALO2_VERIFIER_CHANGES.md).

### Dealing with heavy computation in Cardano transactions

Another challenge was that this verification is very heavy and consumes
a large number of execution units. As a result, both our minting
transaction and the one used to update the stake distribution exceeded
Cardano's execution-unit limit. To solve this we had to split the
verification of each Mithril proof into two parts (`phase1` and `phase2`)
that have to be executed sequentially. In the current flow this happens
each time the stake distribution is updated, and for each minting transaction, producing a
`proof_receipt` UTxO every time. Each UTxO that holds the `phase2` result carries an NFT that
identifies the verified proof and binds it with the corresponding
Mithril certificate. The downstream transactions that still depend on
those proof receipts (`stake_distribution_standard_tx` and
`bridge_mint_tx`) consume the corresponding `proof_receipt` inputs
instead of running the Mithril STM verification inside those
transactions. More details in
[bridge-aiken/2_phase_mithril_stm_verification.md](bridge-aiken/2_phase_mithril_stm_verification.md).

## Handling Cardano's transactions size limit

Another problem was caused by Cardano's per-transaction size limit. The
scripts we use to validate Mithril certificates and to verify the
different ZK proofs the bridge requires are big, and putting all of
them in the same transaction pushed it over the size limit. The
solution we found was to use **reference scripts** in our transactions.
That way we have UTxOs that hold the scripts, and the bridge's
transactions only carry references to them.

## Verifying a Mithril genesis certificate

We also added verification of a genesis certificate's
signature. This was not in the project's initial scope, but we decided it was
important to include since it is an important aspect of the bridge.
To do this we had to handle both the current case, where a Mithril
certificate carries an Ed25519 signature, and the case Mithril is currently
rolling out, where it will be a Schnorr signature (initially, certificates
will carry both signatures).

Genesis verification is invoked from the stake-distribution mint validator
(`stake_distribution_validator_mint`) through `verify_mithril_genesis_certificate`,
which also checks that the certificate's epoch matches its protocol message.

The Ed25519-only case was straightforward to implement in an Aiken validator:
it checks the signature against the genesis verification key stored in
`env/default.ak` (see `verify_with_genesis_vkey`). The dual-signature case is a
bit more difficult.

### Dual genesis certificate

This is experimental: dual signatures are not in Mithril production yet. Such a
certificate carries both signatures (the Ed25519 one and the Schnorr one over
the JubJub curve), and both must be verified on-chain.

We first tried verifying both signatures directly in Aiken (that work lives in
`experimental_dual_genesis_certificate_verifies`), but the validator far
exceeded Cardano's CPU limit, because the Schnorr signature uses the JubJub
curve, which is not implemented in Cardano. To solve this, the Schnorr
verification is performed off-chain in a ZK circuit and only the resulting
Groth16 proof is verified on-chain; the Ed25519 half is still checked natively.
This can be seen in `verify_with_genesis_vkey` (the `GenesisDualSignature`
case, which combines the native Ed25519 check with
`verify_dual_genesis_signature_against_groth16`); the circuit and its implementation details
can be found in the `circuit_jubjub_schnorr_verification` folder.

# Local testing

The whole flow runs locally against a Dolos node, which gives us a Cardano-faithful
validation pipeline (phase-1 + phase-2 ledger rules, real script
evaluation) without paying for testnet ada or waiting for blocks.
Testing happens at two layers. For a full walkthrough of the harness, including
the role of every high-level script, the bundle/artifact shapes that
flow through the pipeline, and the runnable commands, see
[bridge-aiken/LOCAL_TESTING.md](bridge-aiken/LOCAL_TESTING.md).

## 1. Aiken unit tests

`aiken check` runs the suite under `bridge-aiken/validators/tests/`,
which covers every validator we ship: minting, stake distribution,
locking-txs updater, snapshot membership, phase 1, phase 2, and an
end-to-end bridge fixture. These exercises are pure validator logic
against handcrafted `ScriptContext`s, so they don't need a node and
are fast enough to run on every change.

## 2. End-to-end against a local Dolos

The full transaction flow described in
[bridge-aiken/BRIDGE_FLOW_DIAGRAM.md](bridge-aiken/BRIDGE_FLOW_DIAGRAM.md)
is built and submitted against a local Dolos through three layers:

1. **Off-chain bundle build.** The Rust generator
   `plutus-halo2-verifier-gen` produces the canonical
   `bridge-compatible-mithril-stm-bundle.json` containing the SNARK
   proofs for the Mithril proof domains
   (`stake_distribution_genesis`, `stake_distribution_standard`,
   `cardano_transactions`). Every other layer reads from this bundle.
   In the current runtime, only `stake_distribution_standard`
   and `cardano_transactions` go through on-chain `phase1/phase2`;
   genesis remains in the bundle for completeness but is consumed
   by the Aiken-native bootstrap path described earlier in this documentation.

2. **Transaction resolution via Tx3.** The 12 templates in
   `bridge-aiken/main.tx3` are resolved into concrete Cardano CBOR
   transactions. The Tx3 CLI (`trix`, installed via `tx3up`) drives 
   that resolution, pulling redeemer data from the bundle and UTxO 
   state from Dolos itself.

3. **Validation and submission via Dolos.** The resolved tx goes
   through `dolos validate` (phase-1 + phase-2 with the bridge's
   custom per-phase tracing) and `dolos submit`. The bridge mint tx
   in particular is rewritten with the realistic Halo2-verifier
   execution units by our custom `patch_bridge_mint_tx` binary
   before submission, and any phase-2 failure can be replayed for
   diagnosis with `phase2_mint_probe`.

## Running the main cases

Everything is wired through a single operator entrypoint at
`bridge-aiken/scripts/bridge.sh`. The main sequence is:

```bash
cd bridge-aiken

# One-time setup: install repo-local trix/cshell tooling and Python deps.
./scripts/bridge.sh bootstrap --link
uv sync

# Recommended short path: workspace/tooling checks, artifact alignment,
# Aiken unit tests, and the integrated runtime flow.
./scripts/bridge.sh run --strict
```

`run --strict` is the recommended entrypoint because it already builds
the Mithril proof export bundle (the JSON file that contains all data needed from the
Mithril certificates to proof their correctness), runs the mandatory preflight, executes
the Aiken unit-test suite, and drives the integrated happy path described in
[bridge-aiken/BRIDGE_FLOW_DIAGRAM.md](bridge-aiken/BRIDGE_FLOW_DIAGRAM.md)
(`phase1/phase2` across the two remaining Halo2 domains, stake distribution, and
bridge mint).

If you want to drive the stages separately, you can still use:

```bash
# Build only the canonical Mithril STM bundle.
./scripts/bridge.sh proof-export-bundle

# Run the integrated flow without the strict preflight-first posture.
./scripts/bridge.sh run
```

If you need to drive a sub-flow on its own (typical when debugging a
specific tx), the same entrypoint exposes:

```bash
./scripts/bridge.sh phase12-all          # the two Halo2-backed phase1/phase2 runs
./scripts/bridge.sh stake-distribution   # sdg + sds runtime txs
./scripts/bridge.sh bridge               # full bridge minting flow
```

Most stages are idempotent over a fixed `--output-dir`: re-running
skips deterministic steps whose fingerprints have not changed. To
mirror exactly what CI runs, use
`./scripts/tests/run_ci_jobs_locally.sh <lane>` (`quick-lane`,
`standard-lane`, `full-lane`).

## Getting the current Mithril genesis verification key

When the bridge needs to validate a Mithril genesis certificate, the
network-specific trust anchor is Mithril's published `genesis.vkey`.

At the time of writing, the canonical raw files are published directly in the
Mithril repository under `mithril-infra/configuration/<network>/genesis.vkey`.

### Preview

Mithril's current Preview network entry is named
`pre-release-preview` upstream.

```bash
curl -s https://raw.githubusercontent.com/input-output-hk/mithril/main/mithril-infra/configuration/pre-release-preview/genesis.vkey
```

### Preprod

```bash
curl -s https://raw.githubusercontent.com/input-output-hk/mithril/main/mithril-infra/configuration/release-preprod/genesis.vkey
```

### Mainnet

```bash
curl -s https://raw.githubusercontent.com/input-output-hk/mithril/main/mithril-infra/configuration/release-mainnet/genesis.vkey
```

### Notes on format

The downloaded value is Mithril's `JsonHex` encoding of the Ed25519 genesis
verification key, not the raw 32-byte key directly.

If you want to inspect the raw Ed25519 bytes locally, you can decode it with:

```bash
python3 - <<'PY'
import ast
import binascii

json_hex = "PUT_THE_VALUE_HERE"
ascii_json = binascii.unhexlify(json_hex).decode()
raw_key = bytes(ast.literal_eval(ascii_json))
print(raw_key.hex())
PY
```

For bridge-aiken specifically, `env/default.ak` stores the decoded raw
Ed25519 verification key bytes, not the upstream `JsonHex` wrapper.
