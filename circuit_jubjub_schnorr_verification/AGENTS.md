# AGENTS.md

## Purpose

This directory is the planned home of a new Circom circuit that verifies the
Mithril genesis **Standard Schnorr signature over Jubjub**, using Groth16 over
BLS12-381 as the proving backend.

The long-term target is integration with:

- `bridge-aiken/validators/stake_distribution.ak`
- `bridge-aiken/main.tx3`
- the `bridge.sh run --strict` runtime flow

## Why this exists

`bridge-aiken` explicitly rejected direct on-chain Jubjub verification in Aiken
pure code after the `jubjub_spike.ak` feasibility run showed prohibitive costs.

So the new plan is:

- verify the Jubjub Schnorr relation inside a Circom/Groth16 proof
- consume that proof from the bridge flow the same way we already consume the
  other auxiliary Circom proofs

## Important scope decision for stage 1

The current standalone circuit works over **algebraic inputs**, not over the
full byte-level Mithril payload yet.

That means the circuit currently expects:

- `message_base`
- `verification_key_u`
- `verification_key_v`
- `signature_response`
- `signature_challenge`
- `challenge_scalar`
- `challenge_quotient`

This is intentional.

It lets us validate the core arithmetic relation first, before adding:

- byte parsing
- SHA-256 packing / unpacking
- public-input packing
- bridge-specific witness export helpers

The `challenge_scalar` / `challenge_quotient` split is a temporary stage-1
choice to keep the reduction from Jubjub base field to Jubjub scalar field
explicit and compilable without committing yet to the final byte-level witness
shape.

Stage-2 consequence:

- the current Rust export path deliberately serializes this same algebraic
  statement, instead of pretending we already have the final bridge-shaped
  packed digest inputs
- this is intentional so the Groth16 plumbing can move forward independently
  from the remaining transcript-alignment work

Also important:

- `fixtures/` are the canonical upstream-oriented vectors
- `examples/` now mirrors the canonical upstream-valid witness used by the
  current strict circuit

## Upstream semantic target

The circuit is intended to mirror these upstream Mithril pieces:

- `mithril-stm/src/signature_scheme/schnorr_signature/standard_signature.rs`
- `mithril-stm/src/signature_scheme/schnorr_signature/verification_key.rs`
- `mithril-stm/src/signature_scheme/schnorr_signature/jubjub/curve_points.rs`
- `mithril-stm/src/signature_scheme/schnorr_signature/jubjub/field_elements.rs`
- `mithril-common/src/crypto_helper/genesis/schnorr.rs`

The key relation is:

- `R' = response * G + challenge_as_scalar * VK`
- `challenge' = Poseidon(DST, VK.u, VK.v, R'.u, R'.v, message_base)`
- `challenge' == challenge`

## Security notes

At this stage, the circuit is not yet wired to Mithril's byte-level encoding.

That means the following are still pending before production use:

- binding `sha256(rigid_preimage)` to `message_base`
- binding signature bytes to:
  - `signature_response`
  - `signature_challenge`
- deciding whether verification key coordinates remain public inputs or are
  tied to the bridge's configured genesis trust anchor in another way

Do not treat the current stage-1 scaffold as production-ready cryptography.
